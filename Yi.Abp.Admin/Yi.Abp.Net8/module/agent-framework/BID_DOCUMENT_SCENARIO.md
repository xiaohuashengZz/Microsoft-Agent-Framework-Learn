## 1. 业务场景全貌

### 1.1 客户需求

客户(招标方)要做一份招标文件,流程是:

```
客户上传项目资料 + 对话描述需求
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  阶段一:智能推荐                                          │
│  系统从多个库并行搜索,推荐多个候选文件给客户选            │
│  - 范本库(模板)                                          │
│  - 历史招标文件库                                         │
│  - 其它资料库                                             │
│  客户从推荐列表中选定一个文件                              │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  阶段二:智能创作                                          │
│  基于选定的文件 + 项目资料,创作招标文件                   │
│  - 智能填充 Word 内容控件(空)                            │
│  - 多个 Agent 并行填充不同部分                            │
│  - 实时展示进度                                           │
│  - 实时展示每页内容                                       │
│  - 可回退某步骤重新执行                                   │
└──────────────────────────────────────────────────────────┘
        │
        ▼
┌──────────────────────────────────────────────────────────┐
│  阶段三:合规审查                                          │
│  多个 Agent 并行审查不同维度                              │
│  - 法律合规                                               │
│  - 技术规范                                               │
│  - 商务条款                                               │
│  根据审查结果调整文档                                     │
└──────────────────────────────────────────────────────────┘
        │
        ▼
    最终招标文件
```

### 1.2 核心挑战与 MSAF 的解法

| 业务挑战 | MSAF 解法 | 对应概念 |
|---------|-----------|---------|
| 三库同时搜索,要快 | 并行执行多个 Agent | Fan-Out |
| 三个搜索结果要合并展示 | 等齐后聚合 | Fan-In |
| 客户要选文件(人工介入) | 暂停等待用户选择 | Human-in-the-loop |
| 文档不同部分同时填 | 多 Agent 并行填充 | Fan-Out |
| 实时看进度 | Workflow 事件 + SignalR | 事件订阅 |
| 实时看每页内容 | 流式输出 + 推送 | RunStreamingAsync |
| 回退某步骤重做 | Workflow 检查点 | Checkpoint |
| 三种审查同时做 | 并行审查 | Fan-Out |
| 流程后续要可调 | 动态构建 Workflow | WorkflowBuilder |
| 每个能力可独立替换 | Agent 插件化 | ChatClientAgent |

### 3.3 关键概念讲解

#### 🔍 查询员为什么是 Agent 而不是直接查库?

```
┌─────────────────────────────────────────────────────────┐
│  当前方案: 数据库存文件路径 + 文件描述(MSAF + LLM)      │
│  ─────────────────────────────────────                  │
│  数据库表结构示例:                                       │
│  ┌──────────────────────────────────────────────────┐  │
│  │ bid_templates                                    │  │
│  │ ┌────┬──────────────┬──────────────────────────┐ │  │
│  │ │ id │ file_path    │ description              │ │  │
│  │ ├────┼──────────────┼──────────────────────────┤ │  │
│  │ │ 1  │ /files/t1.docx│ 市政道路改造工程模板,含 │ │  │
│  │ │    │              │ 道路/排水/照明章节        │ │  │
│  │ │ 2  │ /files/t2.docx│ 城市主干道建设工程模板, │ │  │
│  │ │    │              │ 含桥梁/隧道章节           │ │  │
│  │ └────┴──────────────┴──────────────────────────┘ │  │
│  └──────────────────────────────────────────────────┘  │
│                                                         │
│  ❌ 直接查库(传统做法):                                │
│  SELECT * FROM templates WHERE description LIKE '%道路%'│
│  问题: 关键词匹配太死板,客户说"市政道路"查不到"城市道路"│
│                                                         │
│  ✅ 用 Agent(MSAF 做法):                               │
│  1. Agent 调 LLM 理解项目语义                           │
│     "市政道路工程" → 理解为:道路/桥梁/排水/照明         │
│  2. Agent 用工具查库(基于路径+描述)                     │
│     - 先用关键词查 description 字段召回候选             │
│     - 再调 LLM 对候选描述语义打分排序                   │
│     - 能找到"城市主干道改造工程"模板                    │
│  3. Agent 调 LLM 给候选打分排序                         │
│     "这个模板匹配度85%,适合市政道路项目"                │
│                                                         │
│  Agent = LLM理解力 + 工具执行力的结合体                 │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  🔮 未来优化: 向量库语义检索(升级方向)                 │
│  ─────────────────────────────────────                  │
│  当前基于"路径+描述"的方案:                              │
│  - 依赖人工维护描述质量                                  │
│  - 关键词召回有限,可能漏掉语义相关文件                  │
│                                                         │
│  未来升级为向量库后:                                     │
│  - 把文件描述/全文切片 → 向量化存向量库                  │
│  - search_xxx 工具改为向量检索,语义相似度匹配           │
│  - Agent 代码基本不变(只换工具实现)                     │
│  - 检索召回率和准确率显著提升                            │
│                                                         │
│  ★ 微内核架构的好处: 换检索引擎=换工具,Agent/Workflow不变│
└─────────────────────────────────────────────────────────┘
```

#### 🔀 Fan-Out 的并行价值

```
串行查询(慢):
  0s ─── 范本库(2s) ─── 2s ─── 招标库(3s) ─── 5s ─── 资料库(1.5s) ─── 6.5s
  总耗时: 6.5秒

并行查询(快):
  0s ─┬─ 范本库(2s) ────┐
      ├─ 招标库(3s) ────┼─→ 汇总
      └─ 资料库(1.5s) ──┘
  总耗时: max(2,3,1.5) = 3秒  ← 快了一倍!
```

### 3.4 对应代码结构

```csharp
// === Agent 定义 ===

// 范本查询员
var templateSearcher = chatClient.CreateAIAgent(
    instructions: "你是范本检索专家。根据项目信息,用 search_templates 工具查找匹配的招标文件模板,返回Top5并说明匹配理由。",
    name: "template_searcher",
    tools: [SearchTemplatesTool]  // 查范本元数据库(路径+描述)
);

// 招标文件查询员
var bidSearcher = chatClient.CreateAIAgent(
    instructions: "你是历史招标文件检索专家。用 search_bids 工具查找相似的历史招标文件,返回Top5。",
    name: "bid_searcher",
    tools: [SearchBidsTool]  // 查招标元数据库(路径+描述)
);

// 其它资料查询员
var referenceSearcher = chatClient.CreateAIAgent(
    instructions: "你是参考资料检索专家。用 search_refs 工具查找相关的法规、标准、规范等资料。",
    name: "reference_searcher",
    tools: [SearchRefsTool]  // 查资料元数据库(路径+描述)
);

// === Workflow 编排 ===
var builder = new WorkflowBuilder();

var dispatch    = builder.AddExecutor(new DispatchExecutor(),    "dispatch");
var tSearcher   = builder.AddAgent(templateSearcher,             "template_searcher");
var bSearcher   = builder.AddAgent(bidSearcher,                  "bid_searcher");
var rSearcher   = builder.AddAgent(referenceSearcher,            "reference_searcher");
var aggregator  = builder.AddExecutor(new RecommendAggregator(), "aggregator");

// Fan-Out: 同时派给3个查询员
builder.AddFanOutEdge(dispatch, [tSearcher, bSearcher, rSearcher]);

// Fan-In: 3路结果汇入聚合器
builder.AddFanInEdge(aggregator, [tSearcher, bSearcher, rSearcher]);

builder.WithOutputFrom(aggregator);
```

### 4.5 为什么填充要并行?

```
┌─────────────────────────────────────────────────────────┐
│  一份招标文件可能有几十个内容控件                        │
│                                                         │
│  串行填充(慢):                                         │
│  技术规格(10s) → 质量标准(8s) → 付款方式(6s) → ...      │
│  30个控件 × 8s = 240秒 = 4分钟                          │
│                                                         │
│  并行填充(快):                                         │
│  ┌─ TechFiller 填10个技术控件(80s)                     │
│  ├─ CommFiller 填10个商务控件(60s)    ← 同时干!        │
│  └─ QualFiller 填10个资格控件(70s)                     │
│  总耗时: max(80,60,70) = 80秒 ≈ 1.3分钟                 │
│                                                         │
│  快了3倍!                                               │
└─────────────────────────────────────────────────────────┘
```

## 6. 流程可配置:微内核的灵活性

### 6.1 当前固定流程

```
[推荐] → [选择] → [创作] → [审查] → [调整]
```

### 6.2 后续可调整的几种情况

```
情况1: 在审查后增加"专家评审"步骤
[推荐] → [选择] → [创作] → [审查] → [专家评审] → [调整]
                                        ↑
                                   新插入的步骤

情况2: 删减"审查"步骤(简单项目不需要)
[推荐] → [选择] → [创作] → [调整]

情况3: 在创作前增加"需求确认"步骤
[推荐] → [选择] → [需求确认] → [创作] → [审查] → [调整]
                  ↑
             新插入的步骤

情况4: 审查拆成两轮
[推荐] → [选择] → [创作] → [初审] → [复审] → [调整]
```

### 6.3 微内核如何支持流程调整

```
┌─────────────────────────────────────────────────────────────┐
│  传统硬编码做法(改流程=改代码):                            │
│  ──────────────────────────────                             │
│  async Task RunAsync() {                                    │
│      await Recommend();                                     │
│      await Select();                                        │
│      await Create();    // 要加步骤?得改这个方法            │
│      await Review();                                        │
│      await Adjust();                                        │
│  }                                                          │
│  → 加步骤要改主流程代码,影响所有调用方                      │
│                                                             │
│  MSAF 微内核做法(改流程=改图):                             │
│  ──────────────────────────────                             │
│  var builder = new WorkflowBuilder();                       │
│                                                             │
│  // 当前流程                                                │
│  builder.AddEdge(recommend, select);                        │
│  builder.AddEdge(select, create);                           │
│  builder.AddEdge(create, review);                           │
│  builder.AddEdge(review, adjust);                           │
│                                                             │
│  // 要加"专家评审"?只需加两行:                             │
│  // builder.AddEdge(review, expertReview);  // 审查后       │
│  // builder.AddEdge(expertReview, adjust);  // 再调整       │
│                                                             │
│  // 主流程代码零改动!                                       │
│  → 流程定义数据化,可存数据库/配置文件,运行时动态加载       │
└─────────────────────────────────────────────────────────────┘
```

```
│  返回: 20条候选(基于关键词匹配,可能有噪音)                  │
│                                                             │
│  阶段B: 排序(Agent层,调LLM,准)                             │
│  ─────────────────────                                      │
│  Agent拿到20条候选的description                             │
│  调LLM: "根据项目'市政道路工程',给以下模板打分(0-1):        │
│         1. 市政道路改造工程模板                              │
│         2. 城市主干道建设工程模板                            │
│         3. ..."                                             │
│  LLM返回: [{id:1, score:0.95}, {id:2, score:0.78}, ...]    │
│  Agent输出Top5                                              │
│                                                             │
│  ★ 优势: 召回靠SQL(快),排序靠LLM(准),兼顾速度与准确        │
└─────────────────────────────────────────────────────────────┘
```

### 11.3 当前方案工具实现示例

```csharp
// search_templates 工具实现(当前:基于元数据库)
AIFunction SearchTemplatesTool = AIFunctionFactory.Create(
    async (string keywords) =>
    {
        // keywords 是 Agent 调 LLM 生成的关键词,如 "道路,排水,照明"
        var keywordList = keywords.Split(',')
                                  .Select(k => k.Trim())
                                  .Where(k => !string.IsNullOrEmpty(k))
                                  .ToList();

        // 用 SqlSugar 查库(关键词 LIKE 匹配 description)
        var query = _db.Queryable<BidTemplate>();
        var orCondition = Expressionable.Create<BidTemplate>();
        foreach (var kw in keywordList)
        {
            orCondition = orCondition.Or(t => t.Description.Contains(kw));
        }
        var candidates = await query
            .Where(orCondition.ToExpression())
            .Take(20)  // 召回Top20
            .ToListAsync();

        // 返回给 Agent,由 Agent 调 LLM 打分排序
        return candidates.Select(c => new {
            c.Id,
            c.FileName,
            c.FilePath,
            c.Description
        });
    },
    "search_templates",
    "根据关键词检索招标文件模板。输入逗号分隔的关键词,返回匹配的模板列表(基于文件描述)。"
);
```

### 11.4 当前方案的优缺点

```
┌─────────────────────────────────────────────────────────────┐
│  当前方案(元数据库 + LLM排序)                              │
│  ─────────────────────────────                              │
│                                                             │
│  ✅ 优点:                                                   │
│  - 实现简单,无需向量库基础设施                              │
│  - 数据库即存即用,无需额外向量化流程                        │
│  - 关键词召回快(SQL LIKE 或全文索引)                       │
│  - LLM排序保证推荐质量                                      │
│  - 适合文件数量不多(<1000)的场景                            │
│                                                             │
│  ⚠️ 局限:                                                   │
│  - 关键词召回依赖 description 字段质量                      │
│    (描述写得差,就召不回来)                                 │
│  - 纯关键词匹配,语义相近但用词不同的可能漏掉                │
│    (如"市政道路" vs "城市主干道")                           │
│  - 文件量大时(>1万),LIKE查询性能下降                      │
│  - 无法基于文件全文内容检索                                 │
│                                                             │
│  💡 适用场景:                                               │
│  - MVP阶段 / 文件量 < 1000                                  │
│  - 文件描述维护规范                                         │
│  - 对召回率要求不是极致                                      │
└─────────────────────────────────────────────────────────────┘
```

### 11.6 升级路径:从元数据库到向量库

```
┌──────────────────────────────────────────────────────────────┐
│  平滑升级路径(微内核架构的价值)                              │
│                                                              │
│  ★ 核心: 只换工具实现,Agent 和 Workflow 代码零改动          │

│  - 调 embedding API 把 description 转成向量                  │
```

### 11.7 两种方案对比

| 维度 | 当前方案(元数据库) | 未来方案(向量库) |
|------|-------------------|------------------|
| **基础设施** | 无需额外组件 | 需部署向量库 |
| **数据准备** | 维护 description 字段 | 离线向量化 |
| **检索方式** | SQL LIKE / 全文索引 | 向量相似度 |
| **召回率** | 中(依赖关键词) | 高(语义匹配) |
| **准确率** | 中高(LLM排序补足) | 高(向量+LLM双重保障) |
| **性能** | 文件少时快,多时下降 | 稳定(向量索引) |
| **维护成本** | 低 | 中(需维护向量索引) |
| **适用规模** | < 1000 文件 | > 1000 文件 |
| **Agent代码** | - | **不变** |
| **Workflow代码** | - | **不变** |
